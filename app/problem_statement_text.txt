1. Background 
Agriculture faces persistent challenges: water scarcity, unpredictable weather, soil degradation, crop 
diseases, inefficient irrigation, and the excessive use of fertilizers and pesticides. Emerging technologies - 
artificial intelligence (AI), computer vision, satellite and weather data, and predictive analytics - can help 
farmers make better, more sustainable decisions. This challenge asks you to turn one such capability into 
a working, verifiable tool, and gives you room to extend it into a broader advisory platform. 
2. Core Problem Statement 
Build an AI-powered crop-disease detection tool that identifies plant diseases from leaf/crop images using 
computer vision, reports its accuracy on a held-out test set we provide, and presents results to a farmer in 
a simple, actionable way. You may then extend it into a broader smart-agriculture advisor by adding any of 
the optional bonus modules in Section 3.2. 
3. Challenge Structure: Core + Bonus 
3.1 Mandatory Core Task (required of every team) 
• Crop Disease Detection (Computer Vision). Accept a leaf/crop image and classify it into a disease class (or 
“healthy”) from the provided label set. Report standard metrics on the provided held-out test set (Section 
4), and surface a clear result plus basic precautionary guidance to the user. 
• Minimum bar. A trained model (transfer learning is encouraged), an honest train/validation/test split, a 
reported macro -F1 and confusion matrix on the held -out test set, and a minimal interface (web app, 
notebook UI, or CLI + screenshots) that runs a prediction on a new image. 
A submission that does not deliver the core task is considered incomplete regardless of how many bonus modules 
it includes.

4. Provided Data & Evaluation Protocol 
4.1 The dataset & the deliberate difficulty 
The core task uses two well-known public datasets in a train-on-lab / test-in-field design. This is intentional: it 
is what makes the challenge above-average. Models that memorise clean laboratory images score in the high-
90s on other lab images but degrad e sharply on real field photos - so the real problem is generalisation, not 
fitting.

• Shared class list. A fixed set of ~15–20 crop–disease classes (plus “healthy”) that exist in BOTH datasets is 
published with the data, e.g. Tomato Early Blight, Tomato Late Blight, Tomato Leaf Mould, Tomato 
Bacterial Spot, Potato Early/Late Blight, Corn Common Rust, Corn Grey Leaf Spot, Apple Scab, Apple Black 
Rot, Grape Black Rot, Bell Pepper Bacterial Spot, and the matching “healthy” classes. The exact final list 
ships with the kickoff data; all teams use it verbatim. 
• Submission / predict interface. Expose a predict( image_path) → class_label function (Python) OR a 
documented CLI (python predict.py --image path) that prints the predicted class. It must load your trained 
weights and run on a single new image with no manual steps. Exact signature and the label-string format 
are published with the data. 
4.2 Primary metric (core task) 
• Macro-averaged F1 on the held -out test set is the primary, objective ranking metric for the core task. 
Macro-F1 is used (not raw accuracy) because disease classes are imbalanced. 
• You must also report a confusion matrix and per-class precision/recall in your model report (Section 7.3). 
 
Data rules for the core task. 
You may add extra public data to your TRAINING set (cite it) and use any data you like for bonus modules. 
But the core task is always evaluated on the organizers' held-out field set via your predict interface. Training 
on the held-out set, or substituting your own test data for the core score, is non-compliant and forfeits the 
AI/ML axis.

7. Submission Contract (GitHub) 
All teams submit a single public GitHub repository link. A submission is judged only if it meets the requirements 
below. Reproducibility is a scored gate: if judges cannot run or verify your core task, the AI/ML axis cannot be 
awarded in full. 
7.1 Required repository structure 
• /README.md - the entry point (see 7.2). 
• /src or /app - source code. 
• /model - training/inference code and the required predict interface from Section 4.1 (weights via 
release/link if large). 
• /report - the one-page model report (7.3). 
• requirements.txt / environment file and clear run instructions. 
7.2 Required README contents 
1. Which core + bonus modules you built. 
2. Setup and run instructions (a judge must reproduce a prediction in under ~10 minutes). 
3. Dataset used and its source/licence (core = provided dataset). 
4. Reported metrics for every model (core: macro-F1 + confusion matrix). 
5. Architecture overview and known limitations. 
6. Link to the demo video (7.4) and to any deployed app. 
7.3 Required model report (one page) 
Field What to state 
Task e.g. crop-disease image classification, N classes. 
Dataset & split Source, sizes, and exact train/validation/test split (core uses the provided 
split). 
Model / approach Architecture, backbone, key hyperparameters. 
Metric & result Macro-F1 (primary) + accuracy, with confusion matrix and per-class 
precision/recall. 
Baseline The provided baseline number and how you compare to it. 
Limitations Honest failure cases (e.g. real-field vs lab images). 
7.4 Demo video (primary evidence) 
• A 3–5 minute recorded demo (unlisted link is fine) is the primary demonstratio. It must show the core 
task running on a new image, plus any bonus modules.

8. Originality & Timeframe Rules 
• All substantive work must be committed between 10 – 15 September. Commit history must reflect real 
development during the window. Repos created before kickoff with pre-built solutions are disqualified. 
• Reuse of open-source libraries, pretrained backbones, and public datasets is allowed and encouraged - but 
must be cited in the README. 
• Copying a public notebook/solution wholesale is prohibited.  Include an originality declaration in the 
README listing any third-party code or notebooks you referenced. 
• AI coding assistants may be used; the working system and its evaluation are what get scored.

10. Tie-Break & Shortlisting 
To produce a clean top-44 cut, ties and near-ties are resolved in this fixed order: 
1. Core-task macro-F1 on the held-out test set (higher wins). 
2. Reproducibility - did the core run cleanly from the README? 
3. Depth and correctness of bonus modules (verified, not merely present). 
4. Innovation score, then judge panel review of the demo.

13. Final Challenge Statement 
AgriSmart AI - Intelligent Agriculture for a Sustainable Future. Build an AI -powered crop -disease 
detection tool (the core task) that classifies plant diseases from images and reports its accuracy on the 
provided held-out test set, presented in a simple, farmer-friendly way. Optionally extend it into a broader 
advisor - crop recommendation, smart irrigation, weather intelligence, a sustainability score, a 
conversational/regional-language assistant, IoT, or an agentic layer. Submissions are judged on a shared, 
objective core metric plus the depth, reproducibility, and impact of what you build, to create an affordable 
and scalable solution with measurable benefit to agricultural productivity and sustainability.
